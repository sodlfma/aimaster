## 1. 프로젝트 개요 · 설계 의도

### Q1. 이 에이전트가 해결하려는 문제를 한 문장으로 말해보세요.

**A.** Apache/Tomcat/DBCP 설정에서 3계층 병목 임계치를 수치로 뽑고, 그 수치에 맞춘 JMeter 부하를 생성·실행·수집한 뒤 JTL·GC까지 한 화면에서 교차 분석하는 **폐쇄 루프(Closed Loop) 성능 진단 에이전트**입니다.

---

### Q2. 왜 “자율형 멀티 에이전트”가 아니라 LangGraph StateGraph로 흐름을 코드가 고정하게 했나요?

**A.** 부하 테스트는 잘못된 대상·잘못된 동시성에 바로 운영 사고가 납니다. LLM이 다음 단계·도구를 자유 선택하면 재현성과 안전 게이트가 깨집니다. 그래서 메인 그래프는 노드/조건부 엣지로 **결정론적으로 고정**하고, LLM은 파싱 보조·해석·시나리오 설계·분석처럼 **허용된 슬롯**에서만 쓰며, 도구 자유 선택은 읽기 전용 `chat_agent` 서브그래프에만 둡니다.

---

### Q3. Streamlit을 “얇은 UI”로 둔 이유는? 상태의 진실의 원천은?

**A.** UI가 비즈니스 상태를 들고 있으면 새로고침·탭 이동·재실행 시 상태가 갈라집니다. Streamlit은 `run_id`(thread_id)로 그래프를 구동하고, `interrupt()` 페이로드를 보여 주며, `Command(resume=...)`로 되돌리는 **드라이버** 역할만 합니다. **Source of truth는 LangGraph 체크포인트(`SqliteSaver`, `thread_id=run_id`)** 입니다. `st.session_state`에는 run_id와 UI 임시값만 둡니다.

---

### Q4. SC-001 / SC-002A / SC-002B / SC-002C를 각각 한 줄로.

| 코드 | 한 줄 |
|---|---|
| **SC-001** | 설정 수집·파싱 → 임계치·부하 플랜·진단 리포트 |
| **SC-002A** | 시나리오 → 순정 JMX 번들 렌더·검증 |
| **SC-002C** | preflight → JMeter 실행 → 결과 수집 |
| **SC-002B** | JTL/GC 집계·이상 탐지·LLM 분석 리포트 |

---

### Q5. Non-Goals(플러그인 의존, 실시간 APM 대체 등)를 둔 이유는?

**A.** 범위를 줄여 **재현 가능한 MVP 폐루프**에 집중하기 위해서입니다. 플러그인(Ultimate/Concurrency TG)은 설치·버전 의존이 커서 사내 표준 배포가 어렵고, 실시간 APM은 에이전트 범위·권한·상시 수집이 완전히 다른 제품입니다. 이 프로젝트는 **Run 단위 사후 분석**에 한정합니다.

## 2. LangGraph · 오케스트레이션

### Q6. `Annotated[list, operator.add]`를 쓴 이유와 장단점?

**A.** `warnings`, `llm_skipped`, `llm_calls`, `node_log`처럼 여러 노드가 **누적**해야 하는 필드에 리듀서를 붙입니다. 노드가 부분 dict만 반환해도 리스트가 덮어쓰이지 않고 append됩니다.

- **장점**: 감사 로그·진단 흔적을 Run 단위로 보존, 병렬/재시도에도 합치기 쉬움  
- **단점**: 실수로 거대 리스트를 계속 붙이면 체크포인트가 비대해짐 → 대용량 본문은 파일(`llm_calls.jsonl`, 아티팩트)로 분리하는 편이 안전

---

### Q7. interrupt() 게이트 3개와 “게이트는 계산하지 않는다” 원칙?

**A.** `gate_review_plan` / `gate_review_scenario` / `gate_confirm_run` — Streamlit 탭 경계와 1:1입니다. 사람은 플랜·시나리오·실행 여부를 **승인·수정**해야 하고, 자동화만으로 부하를 쏘면 안 됩니다.

게이트는 `interrupt(payload)`로 멈추고, resume 값을 Pydantic으로 검증해 state에 **기록만** 합니다. 임계치 재계산·JMX 렌더·실행은 이후 deterministic/LLM 노드가 담당합니다. 계산을 게이트에 넣으면 UI 재개 경로와 노드 책임이 섞여 테스트·시간여행이 어려워집니다.

---

### Q8. `Command(resume=...)` vs `update_state(as_node=...)`?

| | resume | update_state(as_node=...) |
|---|---|---|
| **언제** | 게이트에서 사용자가 승인·편집 후 이어서 진행 | 특정 노드 “이후”부터 다시 타고 싶을 때 (설정값 수정, 제안 플랜 반영) |
| **효과** | interrupt에 값을 넣고 그래프 재개 | 체크포인트 상태를 고치고, 지정 노드를 이미 끝난 것처럼 보고 다음부터 실행(fork/재실행) |

사이드바의 시간여행/fork도 체크포인트 API 위에 있습니다.

---

### Q9. SqliteSaver + `thread_id=run_id`로 가능해진 것?

**A.** Run마다 영속 상태 → 프로세스 재시작 후에도 **같은 run_id로 재개**, 과거 스냅샷으로 **시간여행**, 분기 **fork**, 게이트에서 멈춘 채 UI만 새로고침해도 동일 지점 복원. 개발 시에는 `MemorySaver`로 대체 가능합니다.

---

### Q10. RetryPolicy를 deterministic I/O와 LLM에 다르게 둔 이유?

**A.** 파일/subprocess 쪽은 `RetryPolicy(max_attempts=2, …, retry_on=(OSError,))`처럼 **일시 I/O**만 짧게 재시도합니다. LLM은 `with_structured_output` + **지수 백오프 수회** 후 **규칙 Fallback으로 반드시 다음 노드 진행** — 무한 재시도로 파이프라인을 멈추지 않습니다. “실패해도 진단·실행 흐름은 닫힌다”가 우선입니다.

---

### Q11. `aggregate_jtl ∥ parse_gc` 병렬 후 `detect_anomalies`?

**A.** JTL 집계와 GC 파싱은 입력이 다르고 서로 의존하지 않아 병렬로 지연을 줄입니다. 둘 다 끝난 뒤 버킷 시계열·GC 이벤트를 맞춰 **규칙 기반 anomaly**를 만들고, 그 결과를 압축해 LLM 분석에 넘깁니다.

---

### Q12. 주요 조건부 라우터 분기 기준?

| 라우터 | 분기 |
|---|---|
| `after_parse` | 필수값 누락 또는 confidence &lt; 0.8 **이고** LLM on → `llm_extract_config`, 아니면 `compute_thresholds` |
| `after_plan` | LLM + interpret → `llm_interpret_diagnosis`, 아니면 바로 `gate_review_plan` |
| `route_scenario_source` | `url` / LLM 설계 / LLM 없으면 빈 템플릿으로 review 게이트 |
| `after_validate` | ok → confirm, 실패 시 LLM explain 또는 scenario 게이트로 복귀 |
| `after_confirm` | `bundle_only` → collect, 아니면 preflight |
| `after_preflight` | blocking 실패 → confirm 게이트로 되돌림, 통과 → run |
| `after_run` | 중지/미완료 → confirm, 정상 → collect |

---

### Q13. `chat_agent` 서브그래프와 메인 그래프 차이?

**A.** 메인은 코드가 흐름·실행 도구(SSH 수집, JMeter 실행)를 쥐고 LLM 노출을 금지합니다. 채팅 서브그래프는 **읽기 전용 도구**(아티팩트·리포트 조회)만 `ToolNode`로 열고, 사용자가 Run 결과에 대해 후속 질의하는 용도입니다. 부하를 다시 쏘거나 설정을 바꾸는 권한은 없습니다.

## 3. 도메인: Web–WAS–DB 병목 모델링

### Q14. `T_db_lock`, `T_queue`, `T_drop` 정의와 의미?

코드(`model/thresholds.py`) 기준:

| 임계치 | 공식 | 의미 |
|---|---|---|
| **T_db_lock** | `dbcp.maxTotal` | DB 커넥션 풀이 포화 → 대기/타임아웃 |
| **T_queue** | `tomcat.maxThreads` | WAS 워커가 가득 차 요청이 큐에 쌓임 |
| **T_drop** | `maxThreads + acceptCount` | 큐까지 초과 → 거절/503에 가까운 영역 |
| **web_cap** | Apache `MaxRequestWorkers` (있으면) | Web 계층 상한 |

LLM은 이 값을 재계산하지 않고, 공식 문자열을 UI·프롬프트 사실로만 씁니다.

---

### Q15. `MaxRequestWorkers < T_drop`이면 Web이 먼저 병목인 이유?

**A.** 클라이언트가 먼저 만나는 게 Apache입니다. Web 동시 처리 한도가 Tomcat이 드롭하기 전보다 작으면, WAS 한계에 도달하기 전에 Apache에서 대기·거절이 납니다. 안티패턴 메시지: “503이 Tomcat보다 Apache에서 먼저 발생”.

---

### Q16. `DBCP maxTotal > Tomcat maxThreads` 리스크?

**A.** 워커보다 커넥션이 많으면 **안 쓰는 DB 커넥션이 낭비**되고, DB 쪽 세션/락 부하만 키울 수 있습니다. 반대로 maxTotal이 너무 작으면 스레드는 놀고 DB 대기만 늘어 `T_db_lock`에서 먼저 무너집니다. 진단은 “계층 용량 정렬”을 봅니다.

---

### Q17. `acceptCount > maxThreads × 2` 위험?

**A.** 큐가 과도하게 길면 사용자는 **이미 실패한 요청을 길게 기다리게** 됩니다. 타임아웃·재시도 폭주·체감 지연이 커지고, “천천히 죽는” 장애가 됩니다.

---

### Q18. `maxWait=-1`(무한 대기)의 영향?

**A.** 풀이 고갈되면 스레드가 **영구 대기**할 수 있어 WAS 전체가 멈춘 것처럼 보입니다. 타임아웃으로 실패를 드러내지 못해 원인 파악도 어렵습니다. 규칙 진단이 명시적으로 경고합니다.

---

### Q19. breakpoint / spike / sla 비교

| 유형 | 목적 | 패턴 | 검증 포인트 |
|---|---|---|---|
| **breakpoint** | DB→WAS→Web 한계 확인 | 4단계 step-up | 계층별 에러 양상·한계점 |
| **spike** | 순간 폭증 생존·복구 | base → 급등 → 복귀 | 503 폭증 여부, 부하 해제 후 자원 반환 |
| **sla** | 비즈니스 목표 동시성 | N_target 기준 3단계 | 목표 구간 TPS/Latency, N_target &gt; T_db_lock이면 사전 경고 |

---

### Q20. breakpoint Step1~4 공식을 그렇게 잡은 이유?

대략적 의도:

1. **0.8 × T_db_lock** — 여유 있는 베이스라인  
2. **1.1 × T_db_lock** — DB 풀을 살짝 넘겨 대기/maxWait 증상  
3. **(T_queue + T_drop) / 2** — WAS 큐잉 구간  
4. **1.2 × T_drop** — 드롭 너머 스트레스·복구력  

“정확히 임계치에 붙이기”보다 **계층을 순서대로 스치며 증상을 드러내는** 설계입니다. ramp/hold는 옵션으로 스케일합니다.

---

### Q21. 붙여넣기 대신 SSH 원격 수집의 장단점?

**장점:** 실제 서버 설정과 일치, 경로 표준화, 운영자가 민감 원문을 채팅에 덜 붙임.  
**단점:** SSH 권한·네트워크·호스트키·래퍼(`SSH_WRAPPER_CMD`) 의존, preflight·허용 호스트와 결합된 보안 복잡도. 비밀번호는 argv가 아니라 ASKPASS로 전달.

## 4. 하이브리드 파싱 · 결정론 vs LLM

### Q22. Regex → (신뢰도&lt;0.8) LLM extract → merge_validate 흐름?

1. `parse_regex`: Apache/Tomcat/DBCP 등 규칙 파싱 + confidence  
2. `after_parse`: 필수 누락 또는 confidence &lt; 0.8 **이고** LLM 켜짐 → `llm_extract_config`  
3. 아니면 LLM/merge를 건너뛰고 `compute_thresholds`  
4. LLM 경로: structured 추출 → `merge_validate`에서 regex와 병합·범위 검증 → 임계치

---

### Q23. 왜 임계치·플랜 수치는 LLM이 재계산하지 못하게 했나?

**A.** 같은 입력에 다른 숫자가 나오면 부하 테스트 신뢰가 무너집니다. “측정·용량 산정은 결정론, 설명·가설은 확률론”이 원칙입니다. LLM은 해석 문장·시나리오 구조·분석 내러티브를 담당합니다.

---

### Q24. LLM 역할 원칙을 예시로?

| 역할 | 예 |
|---|---|
| 파서 보조 | regex가 못 채운 `maxTotal`을 원문 근거와 함께 제안 |
| 해석가 | 안티패턴·임계치를 운영자 언어로 설명 |
| 시나리오 설계자 | URL이 아닌 자연어 요구를 `ScenarioSpec`으로 |
| 분석가 | anomaly·버킷 요약을 바탕으로 병목 가설·다음 액션 |

계산기 역할(예: “T_drop을 다시 구해줘”)은 Python 노드가 합니다.

---

### Q25. structured output + 재시도 + rule Fallback 이점?

**A.** 스키마 깨진 JSON을 줄이고, 일시 오류는 재시도, 그래도 실패하면 **규칙 리포트/빈 LLM 결과로 전진**합니다. 오프라인·사내망 장애에서도 진단→빌드→실행→규칙 분석까지 막히지 않습니다.

---

### Q26. host/port/protocol을 사용자 입력으로 강제하는 이유?

**A.** LLM이 환각한 호스트로 부하를 보내면 **잘못된 서버 공격**이 됩니다. 시나리오 설계 후에도 target은 사용자/게이트가 확정한 값을 덮어씁니다. preflight `allowed_hosts`와 같은 안전 계층입니다.

---

### Q27. LLM 없이도 전 파이프라인이 돈다는 의미?

**A.** 규칙 파싱·임계치·플랜·JMX·실행·anomaly·규칙 진단 리포트로 **폐루프가 완성**됩니다. 테스트는 fake JMeter + 가짜 LLM으로도 가능하고, CI/데모/폐쇄망에서 실용적입니다. LLM은 품질을 올리는 **가산기**이지 SPOF가 아닙니다.

---

## 5. JMeter 연동 · 실행

### Q28. 왜 순정 ThreadGroup 직렬인가?

**A.** 플러그인 배포·버전 파편화를 피하고, 사내 어디서나 `jmeter -n`만으로 재현합니다. 4단계는 **순정 ThreadGroup을 직렬**로 두어 step-up을 표현합니다.

---

### Q29. `${__P()}` 속성 외부화?

**A.** 동시성·호스트·경로 등을 `user.properties` / `-J`로 빼고 JMX는 골격만 유지합니다. **JMX 재생성 없이** 숫자만 바꿔 재실행할 수 있고, 번들(`plan.jmx`, `user.properties`, `run.sh`)이 그 계약을 담습니다.

---

### Q30. 실행 모드 차이?

| 모드 | 용도 |
|---|---|
| **local** | 에이전트 머신에서 `jmeter -n` |
| **docker** | 이미지로 CLI 실행 |
| **remote** | 분산 `-R` 등 |
| **bundle_only** | 번들만 만들고 외부 실행 JTL 업로드 분석 |

---

### Q31. `allowed_hosts` blocking · SSH 호스트 자동 허용?

**A.** 실수로 운영/외부 호스트에 부하를 쏘는 것을 **실행 직전 하드 스톱**합니다. SC-001에서 SSH로 진단한 호스트는 “이미 작업 대상으로 확인된 서버”이므로 같은 Run에서 자동 허용해 UX를 해치지 않습니다. 다른 호스트는 목록/UI에서 명시 추가합니다.

---

### Q32. AWS 공인 IP hairpin?

**A.** 같은 인스턴스의 EIP로 나가면 NAT hairpin으로 TCP가 실패할 수 있습니다. preflight가 IMDS 등으로 공인 IP를 조회해 대상이 자신이면 `localhost` 사용을 안내합니다.

---

### Q33. 백그라운드 스레드 + `get_stream_writer`(Summariser)?

**A.** JMeter는 수 분~수 십 분 동안 돌아가 Streamlit 요청을 블로킹하면 UX가 죽습니다. 백그라운드에서 그래프를 돌리고, Summariser 라인을 커스텀 스트림으로 보내 **1초 주기 fragment**로 진행률을 갱신합니다.

---

### Q34. `runs/<run_id>/STOP` 중지 방식?

**장점:** 프로세스 간/스레드 간 단순 협약, 체크포인트와 독립, UI·시그널에서 파일만 만들면 됨.  
**단점:** 폴링 지연, 파일 권한, JMeter가 즉시 안 죽을 수 있음 → `after_run`에서 stopped면 confirm 게이트로 돌려 재시도/정리합니다.

---

### Q35. 부하 생성기와 WAS 동일 인스턴스 오염?

**A.** JMeter 자체가 CPU·NIC·FD를 많이 써서 **대상과 측정기가 자원을 다툼** → TPS/Latency가 실제 서비스 한계가 아닌 부하기 한계로 왜곡됩니다. 에이전트+JMeter와 WAS/DB는 분리합니다.

---

### Q36. `nofile` / `ip_local_port_range` 미조정 시 오탐?

**A.** Step 3~4 고동시성에서 부하기 쪽 `Too many open files`·로컬 포트 고갈이 납니다. 증상은 대상 장애처럼 보이지만 **클라이언트 한계**입니다. README가 ulimit·sysctl 튜닝을 요구하는 이유입니다.

---

## 6. 사후 분석 (JTL · GC)

### Q37. 컨텍스트 압축이 필요한 이유?

**A.** raw JTL은 수십만 행이라 토큰·비용·노이즈가 큽니다. 시간 버킷(기본 수 초)으로 p99·TPS·에러율을 줄인 뒤 LLM에 넣으면 **신호 대 잡음**과 비용이 개선됩니다. 숫자 집계는 pandas, 서사는 LLM.

---

### Q38. 규칙 anomaly vs LLM 리포트 역할 분담?

**규칙:** latency × baseline, err_rate, HTTP 503, TPS drop, Full GC 구간 등 **재현 가능한 탐지**.  
**LLM:** 주 병목 계층 가설, 근거 연결, 다음 실험 제안 등 **해석**. 규칙이 팩트, LLM이 내러티브.

---

### Q39. GC와 JTL 교차 분석 가설 예?

**A.** 특정 Step에서 p99가 튀는 구간과 Full GC pause가 겹치면 **할당/힙 압박이 지연 원인**일 수 있음. GC 없이 에러율만 오르면 풀·큐·503 쪽을 의심. “지연 = 무조건 GC”가 아니라 **시간 정렬로 기각/채택**합니다.

---

### Q40. Step 경계를 JTL에서 어떻게 복원?

**A.** 스레드 이름 규약: `'Step 3 (WAS Queueing) 1-17'` → 마지막 `스레드그룹-스레드` 토큰을 떼고 `'Step 3 (WAS Queueing)'`을 step 라벨로 씁니다(`jmeter/jtl.py`의 `step_from_thread_name`). TG 이름에 Step을 심어 둔 계약입니다.

---

## 7. 보안 · 운영 · 설정

### Q41. Masker 가역 마스킹 · 토큰 안정성?

**A.** 호스트/IP/JDBC/USER가 조직 밖으로 나가기 전에 `HOST_1` 등으로 바꿉니다. **같은 Run·같은 Masker 인스턴스**에서 토큰이 안정적이어야 LLM이 “HOST_1의 풀”처럼 일관 언급하고, 응답을 unmask할 수 있습니다.

---

### Q42. SSH 비밀번호를 ASKPASS로?

**A.** argv·프로세스 목록·쉘 히스토리에 비밀번호가 남지 않게 하기 위함입니다. `SSH_ASKPASS` + 전용 헬퍼로 OpenSSH에만 전달합니다.

---

### Q43. 비밀값을 Settings 싱글톤에만?

**A.** 체크포인트·`state.json`은 디스크에 남고 공유·디버그에 노출되기 쉽습니다. API 키·SSH 비밀번호는 **프로세스 메모리 Settings**에만 두고 그래프 state에 넣지 않습니다.

---

### Q44. Streamlit 로그인 없을 때 8501 보호?

**A.** 보안 그룹에서 작업자 IP만 허용하거나, **SSH 터널**(`-L 8501:127.0.0.1:8501`)만 사용. 공개 8501은 사실상 무인증 원격 셸에 가깝습니다.

---

### Q45. Talent Lab(`atl-`) vs OpenAI 호환 `/v1`?

**A.** `atl-` 키이거나 Talent Lab 호스트면 Azure deployment 스타일(`api-key` 헤더, `/openai/deployments/{model}/chat/completions`)로 보냅니다. Base URL이 `/v1`로 끝나는 다른 게이트웨이는 OpenAI 호환 Chat Completions입니다. `atl-`를 공개 api.openai.com으로 보내면 401이 나므로 코드가 경로를 갈라줍니다.

---

## 8. 테스트 · 품질 · 확장

### Q46. fake_jmeter / 가짜 structured-output 전략?

**A.** CLI Summariser·합성 JTL/statistics를 흉내 내어 JMeter 실설치 없이 실행 노드를 검증하고, LLM은 가짜 structured 모델로 마스킹·재시도·Fallback·host 고정 규칙을 검증합니다. **결정론 폐루프를 CI에서 닫는 것**이 목표입니다.

---

### Q47. 가장 깨지기 쉬운 부분은?

**모범 답 (하나를 고르고 이유를):**  
- **설정 파서:** 템플릿·주석·멀티 값이 조금만 달라도 confidence/누락이 흔들림  
- **JMX 템플릿·검증:** JMeter 마이너 버전·XML 스키마  
- **게이트·UI resume 계약:** 페이로드 스키마 불일치 시 재개 실패  

본인 작업 영역(파서/그래프/실행기)에 맞춰 “관측한 실패 모드”를 말하면 설득력 있습니다.

---

### Q48. 분산(-R) · 멀티 WAS 팜 확장?

**A.** state의 `target_info`/시나리오를 단일 호스트에서 **호스트 리스트·가중치**로, preflight·allowed_hosts를 전 대상으로, JMX에 다중 HTTP Request 또는 여러 TG, 임계치는 인스턴스당 vs 팜 합산 모델을 분리, runner는 `-R`과 결과 병합(JTL concat) 노드를 추가. 그래프 토폴로지는 유지하고 **모델·preflight·render·collect**를 확장하는 편이 LangGraph 구조와 맞습니다.

---

### Q49. LangSmith 대신 `llm_calls.jsonl` 기본인 이유?

**A.** 사내망·보안 정책상 외부 트레이싱이 막히거나 Off가 기본인 경우가 많습니다. 로컬 JSONL은 Run 디렉터리에 남아 **감사·디버그·재현**에 충분하고, LangSmith는 옵션입니다.

---

### Q50. 왜 LangGraph인가? Airflow/Temporal/자체 FSM이면?

**요약 비교:**

| 대안 | 부족한 점 / 과한 점 |
|---|---|
| **Airflow** | 배치·DAG에 강하지만 HITL interrupt·토큰 스트림·LLM structured 루프와 거리가 있음 |
| **Temporal** | 장기 워크플로·신뢰성에 강하나 인프라 무겁고, 이 앱 규모엔 과함 |
| **자체 FSM** | interrupt/체크포인트/시간여행/조건부 엣지를 다시 구현해야 함 |
| **LangGraph** | Python 상태머신 + HITL + 체크포인트 + LLM 노드가 **한 프로세스 앱**에 맞음 |

핵심 답: “부하 진단 앱에 필요한 HITL·재개·LLM 슬롯을 최소 인프라로 얻기 위해”.

---

## 9. 꼬리질문 · 깊이 확인용

### Q51. merge_validate에서 regex와 LLM이 충돌하면?

**A.** **regex가 이깁니다.** LLM 값은 해당 필드가 `None`일 때만 후보가 되고, 원문에 값 문자열이 존재·evidence가 있을 때만 채택합니다. 근거 없으면 폐기하고 warning을 남깁니다. 범위 밖·Xms&gt;Xmx 등은 무효화합니다.

---

### Q52. 게이트에서 load_plan 수정 시 이후 어느 노드부터?

**A.** `gate_review_plan` resume으로 `load_plan`이 state에 반영되면, 라우터에 따라 시나리오 소스 → 빌드 쪽으로 **이어서** 갑니다(임계치 노드는 다시 안 탐).  
Tab1에서 설정값을 고칠 때는 UI가 `update_state(..., as_node="merge_validate")`로 **병합 이후부터** 임계치·플랜을 다시 계산하게 합니다. “승인 재개”와 “중간부터 재계산”을 구분해서 말하세요.

---

### Q53. validate_jmx 실패 루프 종료 조건?

**A.** `after_validate`: 실패면 LLM explain(또는 바로) `gate_review_scenario`로 돌아가 사용자가 spec을 고칩니다. **validation.ok**가 될 때까지 빌드↔리뷰를 반복하고, ok면 `gate_confirm_run`으로 탈출합니다. 사용자가 시나리오를 포기하고 Run을 버리는 것도 UI 수준 종료입니다.

---

### Q54. warnings / llm_skipped / llm_calls 누적 이유?

**A.** 운영자가 “왜 기본값이 들어갔는지”, “어느 LLM 노드를 건너뛰었는지”, “토큰·실패 여부”를 Run 단위로 추적해야 합니다. 재현·감사·프롬프트 개선의 근거가 되고, 리포트·사이드바 진단에 노출됩니다.

---

### Q55. “측정은 결정론, 설명은 확률론”으로 아키텍처 요약?

**A.** 파싱 병합·임계치·부하 플랜·JMX·preflight·실행·버킷 집계·anomaly는 **같은 입력이면 같은 출력**이어야 하는 측정 경로입니다. LLM은 그 위에 얹힌 **설명·가설·시나리오 초안**이며, 실패해도 Fallback으로 측정 경로는 닫힙니다. 이 한 줄이 그래프 분리·마스킹·host 고정의 설계 이유를 관통합니다.
